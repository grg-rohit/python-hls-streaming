# Architecture

## Overview

The project is split into two independent pipelines that share a single folder on disk:

```
┌─────────────────────────────┐       ┌──────────────────────────────┐
│    CONVERSION PIPELINE      │       │      SERVING PIPELINE        │
│                             │       │                              │
│  videos/source.*            │       │  Browser (hls.js)            │
│       │                     │       │       │                      │
│       ▼                     │       │       │ HTTP GET             │
│   FFmpeg (NVENC / CPU)      │       │       ▼                      │
│       │                     │       │  FastAPI (Uvicorn)           │
│       ▼                     │       │       │                      │
│  streams/                   │──────▶│       │ StaticFiles mount    │
│    master.m3u8              │  disk │       ▼                      │
│    360p/  480p/  720p/ …    │       │  streams/master.m3u8         │
│                             │       │  streams/720p/segment_*.ts   │
└─────────────────────────────┘       └──────────────────────────────┘
```

The two pipelines never run at the same time. Conversion writes files to `streams/`. The server only reads them. There is no shared memory, no queue, no database.

```
python-hls-streaming/
│
├── app/
│   ├── __init__.py
│   ├── main.py              ← FastAPI application (HTTP layer)

├── public/

├── videos/                  ← Drop any video file here (any name, any format)
├── streams/                 ← Generated by FFmpeg, read by FastAPI

├── docker-compose.yml       ← Defines converter, converter-gpu, server services
└── requirements.txt         ← fastapi + uvicorn only
```

## Docker service model

All three services use the same Docker image. The only difference is the command and whether the Nvidia runtime is passed in.

```
docker-compose.yml
│
├── converter          → python convert_video.py --mode cpu
│   └── volumes: videos/ streams/
│
├── converter-gpu      → python convert_video.py --mode gpu   (default)
│   ├── volumes: videos/ streams/
│   └── deploy.resources: nvidia GPU device
│
└── server             → python run.py
    ├── ports: 8000:8000
    └── volumes: videos/ streams/ public/
```

The `public/` volume on the server service means you can edit HTML/CSS/JS without rebuilding the image.

## Request flow (browser → server → disk)

```
Browser
  │
  │  GET /
  ▼
FastAPI (main.py)
  │  FileResponse → public/index.html
  │
  │  GET /static/player.js
  ▼
StaticFiles mount (/static → public/)
  │  Returns public/player.js
  │
  │  GET /api/stream-info
  ▼
stream_info() endpoint
  │  calls available_qualities() → scans streams/ directory
  │  returns JSON: { qualities: ["240p","360p",...], streams_ready: true }
  │
  │  GET /streams/master.m3u8
  ▼
StaticFiles mount (/streams → streams/)
  │  HLS middleware sets Content-Type + no-cache headers
  │  Returns streams/master.m3u8
  │
  │  GET /streams/1080p/segment_042.ts
  ▼
StaticFiles mount (/streams → streams/)
  │  HLS middleware sets Content-Type: video/mp2t
  │  Returns binary TS segment
```

## CORS and headers

The server applies two cross-cutting concerns via middleware:

**CORS** — `CORSMiddleware` allows `*` origins on GET/HEAD/OPTIONS. This is required for:
- LAN devices (different origin IP)
- ngrok tunnels (different domain)

**HLS headers** — a custom middleware intercepts every response:
- `.m3u8` → `Content-Type: application/vnd.apple.mpegurl` + `Cache-Control: no-store`
- `.ts`   → `Content-Type: video/mp2t`

The no-cache header on playlists is important during development — without it, browsers aggressively cache `.m3u8` files and never see updated playlists after re-conversion.
